## Aniqlangan va tuzatilgan muammolar

| Muammo | Oldingi natija | Tuzatish va dalil |
|---|---|---|
| Yuqori: parallel refresh | SQLite `FOR UPDATE` qulf bermagani uchun ikkala so‘rov 200, ikkita aktiv voris | O‘qishdan oldin DB tranzaksiya qulfi va shartli consume. Mustaqil connectionlarda 200/401; reuse butun family’ni yopadi |
| Yuqori: refresh/logout poygasi | Logout 200 dan keyin kechikkan refresh sessiyani tiriltirgan | Ikkala amal bir DB qulfidan foydalanadi; har ikki bajarilish tartibi testda tekshiriladi |
| Yuqori: Bearer-only logout | Cookie bo‘lmasa 200, access esa hali yaroqli | Imzosi tekshirilgan access’dagi family ham revoke qilinadi; boshqa login family’si saqlanadi |
| O‘rta: deactivate/role va auth poygasi | Tekshirish bilan sessiya yaratish orasida holat o‘zgarishi mumkin | Account update, login, refresh va CRM mutatsiyalari uchun umumiy tranzaksiya chegarasi. Deaktivatsiya/rol barcha family’larni revoke qiladi; reaktivatsiya eski tokenlarni tiklamaydi |
| O‘rta: parallel admin/bootstrap | Count/check va yozish atomar emas | Shu company qulfi oxirgi admin va bir martalik bootstrap’ni himoyalaydi; parallel testlar bor |
| O‘rta: brauzer tablari va kechikkan refresh | Promise faqat bitta tabda, logoutdan keyingi javob access’ni qayta saqlashi mumkin | Web Locks, BroadcastChannel va avlod tekshiruvi; Chrome’da ikki tab hamda boshqarilgan kechikish sinovlari |
| O‘rta: Vite proxy Origin’ni almashtirgan | Backend asl browser originini ko‘rmagan | Host/Origin saqlanadi; begona Origin bilan same-site so‘rov 403 |
| Past: token javoblarida cache cheklovi yo‘q | Maxfiy javob uchun no-store aniq berilmagan | Auth/CRM/admin javoblarida `Cache-Control: no-store` |
| Migratsiya mosligi | PostgreSQL Boolean maydoniga `is_active=0` SQL | `FALSE` ishlatiladi; eski `postgres://` URL Alembic’da ham normallashtiriladi. Real PG testi hali yo‘q |

`get_current_user` har so‘rovda user aktivligi, kompaniya, sessiya muddati va server revocation holatini tekshiradi. RBAC rolni JWT’dan emas, bazadagi hisobdan oladi. CRM/admin resurs qidiruvlari company bilan scope qilinadi. Foreign company lead/unit/user uchun 404, Viewer yozishlari uchun 403, anonim yoki yaroqsiz token uchun 401 tekshirildi. Public katalog va murojaatlar login talab qilmaydi. Refresh bazada SHA-256 xesh, parol esa Argon2 bilan saqlanadi; raw token auditga yozilmaydi.

**Amaliy misol:** sotuvchi kirgach refresh tokenlari A → B → C zanjiri hosil bo‘ladi. A yana yuborilsa, server o‘g‘irlangan token bilan tasodifiy takroriy yuborishni ajrata olmaydi, shu zanjirni to‘liq yopadi. Bu qat’iy reuse detection. Qonuniy ikkita tab bir cookie’ni bir vaqtda ishlatmasligi uchun frontend ularni navbatlaydi. Server qulfi esa frontendni chetlab o‘tgan parallel so‘rovlarni ham himoyalaydi.

## Rasmiy asoslar

- SQLite `BEGIN IMMEDIATE` boshqa yozuvchi bilan parallel tranzaksiyani boshlashni cheklaydi: [SQLite transaction hujjati](https://www.sqlite.org/lang_transaction.html).
- PostgreSQL qator qulflari tranzaksiya tugaguncha saqlanadi: [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html).
- Refresh rotation va replay aniqlanganda aktiv refreshni revoke qilish tamoyili: [RFC 9700, §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2). Bu loyiha OAuth authorization server implementatsiyasi degan da’vo emas; sessiya himoyasi tamoyili qo‘llanadi.
